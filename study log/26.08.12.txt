어플리케이션 결함 조치 우선순위 결정

여러개의 결함이 동시에 발생할 수 있다.
모든 결함을 동시에 수정할 수 없다면 업무 영향도와 심각도를 고려하여 어떤 결함부터 해결할지 결정해야 한다

소프트웨어 테스트 기법
1. 단위 테스트 기법
JUnit을 활용한 테스트
- java환경에서 JUnit이라는 단위 테스트 프레임워크를 이용하여 단위 테스트를 수행할 수 있어야 한다
- 테스트 대상 프로그램을 직접 실행하여 결과를 눈으로 확인하는 대신 테스트 코드를 작성하여 예상 결과와 실제 결과를 비교하는 것

Mock 테스트
- Mock 객체를 사용하여 테스트하는 기법
- 특정 기능이나 모듈의 응답 결과를 미리 정의하여 테스트하기 때문에, 특정 모듈 또는 기능이 완전히 개발되지 않은 상태에서도 테스트를 수행할 수 있다.

테스트 더블(Test Double)
- 테스트를 위해 실제 객체 대신하여 사용하는 테스트 전용 객체
Dummy
메서드를 호출하기 위해 객체가 필요해서 넣어 놓지만 실제 테스트에서는 사용하지 않는 객체

public void registerUser( User user, EmailService emailService){ ... };

더미 객체 생성
EmailService dummyEmailService = new EmailService();
registerUser(user, dummyEmailService)

Fake
- 더미보다는 한 단계 더 실제 객체에 가까운 객체
- 실제로 동작하는 구현체이지만 운영 환경에서 사용하는 실제 구현체보다 단순하게 만들어진 객체

DB를 연결한 것 처럼 보이기 위한 ArrayList와 CRUD 기능을 하는 메서드

public class FakeUserRepository{
	private List<User> users = new ArrayList<>();

	저장하기
	public void save(User user){
		users.add(user);
	}

	유저 한명 찾기
	public User findById(int id){
		return users.stream().filter(user -> users.getId() == id).findFirst().orElse(null);
	}

}

Fake는 가짜지만 실제 기능을 어느 정도 수행하는 객체

Stub
- 테스트에 필요한 정해진 결과를 반환한다

public class StubUserRepository{
	public User findById(int id){
		return new User(1, "홍길동","VIP");
	}
}

- 내가 테스트 하고 싶은 상황을 만들기 위해 원하는 결과를 반환하는 것이 목적

Mock
- Stub보다 한 단계 나아간 형태
- 단순히 결과를 반환하는것 뿐만 아니라 테스트 대상 객체가 다른 객체를 올바른 방법으로 호출했는지 검증하는 데 사용
- Mock에서는 호출 행위가 중요하다

2. 통합 테스트 기법
- 전체 시스템이 완성될 때까지 단위 시스템 간의 연계성과 기능 요구사항을 확인하며, 하드웨어와 소프트웨어 구성 요소 간의 상호 작용을 테스트하는 것을 주요 목적으로 한다
- 특히 업무 간 연계성과 상호운용성을 중심으로 테스트한다.

테스트 설계 기법
- 요구사항, 요구사항 명세서, 업무 구조, 시스템 구조를 기반으로 어떤 부분을 어떤 방법으로 테스트 할지 결정하는 활동이다
- 테스트 상황과  방법을 구체화하여 테스트 케이스를 작성하는 것을 테스트 구현이라고 하며, 테스트 상황과 방법을 구체화하기 위한 수단과 도구를 테스트 설계 방법이라고 한다

테스트 설계 방법
보다 작은 케이스 
- 동등 클래스(동등 분할)
수많은 입력값을 동일한 결과가 나올 것으로 예상되는 그룹으로 묶고, 각 그룹에서 대표값만 골라 테스트하는 방법이다

비밀번호는 8자 이상 20자 이하

1 ~ 7자리 : 불가능
8 ~ 20자리 : 가능
21 ~ : 불가능

각 그룹에서 숫자를 하나씩 뽑아서 테스트
- 모든 값을 테스트하지 않고도 프로그램의 기본적인 입력처리를 확인할 수 있다

보다 많은 버그 찾기
- 경계 테스트(경계값 분석)
테스트 케이스를 무작정 많이 만드는게 아니라, 오류가 발생할 가능성이 높은 값을 집중적으로 테스트하자
프로그램의 오류는 정상적인 범위의 중간보다 조건이 바뀌는 경계 근처에서 많이 발생한다

20세 이상 60세 이하는 가입 가능

테스트 대상을 빠짐없이 실행하기
모델 기반 테스트 설계
- 프로그램의 동작이나 상태를 모델로 표현하고, 그 모델을 기반으로 테스트 케이스를 만드는 방법
- 상태 전이 테스트 모델 등을 UML의 State Chart Diagram으로 표현하여 노드와 링크를 대상으로 테스트한다
- 또는 모든 테스트 요소를 매트릭스 형태로 나열하여 빠짐없이 테스트한다

상태 전이 테스트
- 올바른 상태 이동과 잘못된 상태 이동을 확인할 수 잇는 테스트
- 프로그램의 현재 상태가 특정 사건에 의해 다른상태로 변경되는 것
- 상태가 바뀌는것을 전이라고 한다

3. 시스템 테스트 기법
- 전체 업무 진행을 총괄할 수 있도록 테스트 절차와 각 프로세스의 세부 업무를 이해해야 하며, 테스트 결과를 분석하여 해결 방안을 제시할 수 있어야 한다

부하 및 성능 테스트
- 많은 사용자가 동시에 접속하여 조회,수정 등의 요청을 발생시킬 때 시스템이 어떻게 동작하는지 확인하는 테스트
- 특히 성능 요구사항에서 정의된 임계점을 넘어 지속적으로 부하가 증가할 때도 시스템이 정상적인 수준의 반응ㄹ 보이는지 확인한다

부하테스트
동시 이용자 수 = TPS X 호출 간격
호출간격 = 응답 시간 + 대기 시간

TPS : 1초당 처리하는 트랜잭션의 수
대기시간(Think Time) : 응답을 받은 후 다음 명령이나 요청을 수행하기까지 사용자가 기다리는 시간이다

CPU 사용률 : CPU가 얼마나 사용되는지
메모리 사용률 : 메모리가 얼마나 사용되는지
오류율 : 전체 요청 중 실패한 비율
처리량 : 일정 시간 동안 처리한 데이터/요청량

쇼핑몰 상품 조회
평상시에는 사용자가 많지 않지만 할인 행사를 시작하면 1000명의 사용자가 동시에 접속할 것으로 예상된다

동시 사용자 : 1000명
테스트 기능 : 상품 목록 조회
평균 응답시간 : 2초 이하
오류율 : 1%이하
테스트 시간 : 10분

장애 복구 테스트
시스템에 의도적으로 장애 상황을 발생 시킨 후, 시스템이 정상 상태로 복구될 수 있는지 확인하는 테스트
- 서버나 DB에 문제가 생겼을 때 다시 정상적으로 서비스를 제공할 수 있는가

웹 서버 장애 : 운영중인 웹 서버 10대 중 1대의 웹 서버를 강제로 종료
웹 어플리케이션 장애 : 실행중인 WAS 인스턴스 8개 중 현재 사용자가 접속중인 1개의 인스턴스를 중지
데이터베이스 장애 : DB 서비스를 강제 종료

보안테스트
- 시스템에 존재하는 보안 취약점을 찾아내고, 외부의 공격이나 비정상적인 접근으로부터 시스템과 데이터를 안전하게 보호할 수 있는지 확인하는 테스트
- 허가받지 않은 사람이 시스템이나 데이터에 접근할 수 있는가?
- 공격을 받아도 중요한 정보가 안전한가?
- 별도의 보안 전문가를 통해 어플리케이션 전체를 검증하는것이 바람직하다
- 보안성 검증은 기능 요구사항과 별도로 해킹이나 침투 공격에 대응할 수 있도록 최신 보안 기술을 반영한 검증이 필요하다

4. 인수테스트 기법
- 최종 사용자가 요구한 기능이 제대로 반영되었는지, 인수 조건에 만족하는지를 테스트 하는 기법
- 요구 기능 만족 여부, 사용 편리성에 대하여 실제 운영 환경에서 실행되며 고객이 주도하는 테스트이다.

결함 관리의 이해
1. 결함 관리 용어
에러(Error)
- 소프트웨어 개발 또는 유지 보수 수행 중에 발생한 부정확한 결과로, 개발자의 실수로 발생한 오타, 개발 명세서의 잘못된 이해, 서브루틴의 기능 오해 등이 있다.

오류(Fault)
- 프로그램 코드 상에 존해하는 것으로 비정상적인 프로그램과 정상적인 프로그램 버전 간의 차이로 인하여 발생되며, 잘못된 연산자가 사용된 경우에 프로그램이 서브루틴으로부터의 에러 리턴을 점검하는 코드가 누락된 것을 말한다.

실패(Failure)
- 정상적인 프로그램과 비정상적인 프로그램 실행 결과의 차이를 의미
- 프로그램 실행 중에 프로그램의 실제 실행 결과를 개발 명세서에 정의된 예상 결과와 비교함으로써 발견한다

결함(Defect)
- 버그, 에러, 오류, 실패 프로그램 실행에 대한 문제점, 프로그램 개선 사항 등의 전체를 포괄하는 용어이다

2. 결함 판단 기준
- 기능 명세서에 가능하다고 명시된 동작을 수행하지 않는 경우
- 기능 명세서에 불가능하다고 명시된 동작을 수행하는 경우
- 기능 명세서에 명시되어 있지 않은 동작을 수행하는 경우
- 기능 명세서에 명시되어 있지 않지만 수행해야 할 동작을 수행하지 않는 경우
- 테스터의 시각에서 볼 때 문제가 있다고 판단되는 경우

테스트 격언
1. 소프트웨어를 완벽하게 테스트하는 것은 불가능하다
- 가능한 입력의 수가 너무 많다
- 가능한 출력의 수가 너무 많다
- 소프트웨어 명세서가 주관적이다
- 소프트웨어 결함도 주관적이다

테스트 양이 많아질수록 결함의 수는 적어지지만 테스트 비용이 올라간다.
테스트 양이 적으면 결함의 수는 많지만 테스트 비용은 적다
최적의 테스트 양을 찾아야 한다

2. 소프트웨어 테스트는  위험을 수반하는 훈련이다
- 가능한 모든 테스트 시나리오와 테스트 케이스를 테스트하지 않을 경우 위험을 감수하기로 했다는 뜻과 같다
- 테스터는 무엇이 중요하고 무엇이 중요하지 않은지 현명한 판단을 해야 한다.

3. 테스트 작업으로 결함이 존재하지 않는다는 사실을 입증할 수 없다
- 테스트를 통해 소프트웨어에 결함이 없다는 것을 보장할 수 없으며, 단지 테스트 결과로 결함이 있다는 사실만을 보여줄 수 있다.
- 테스트 결과 결함이 발견되지 않았다 하더라도 이는 결함이 없음을 의미하는 것은 아니다

4. 모든 결함을 수정할 수는 없다
- 쫓기는 작업 일정
- 외부적인 요인(테스트 환경 미비, 사용자 환경 자체 장애, 법률 또는 규정 변경 등)으로 결함이 아님에도 결함으로 판단되는 경우
- 각각의 프로그램 간에 서로 결합도가 높은 경우의 고치기 위험한 결함
- 현실에서 거의 발생할 가능성이 없는 경우의 고칠가치가 없는 결함

5. 발견한 결함이 많을수록 남아 있는 결함의 수도 많다

소프트웨어 테스터의 역할과 능력
1. 소프트웨어 테스터의 역할
- 가능한 결함을 빨리 발견하여 결함이 수정 보완되었는지 확인하는 것

2. 소프트웨어 테스터의 능력
- 탐구심과 문제 해결력을 갖춰야 한다
- 때로는 창의력을 발휘하여 결함을 찾기 위해 새로운 접근법도 사용해야 한다
- 완벽함을 추구하지만, 가능한 한도 내에서 적당한 수준의 완벽성을 추구한다.
- 테스터는 항상 나쁜 소식을 전하는 사람이기 때문에, 개발자에게 말을 잘 해야 한다

취약점 발견 후 발견된 취약점을 분석하고 개선 방안을 수립한다
개선 내용을 시스템에 반영한 후 다시 검증한다

인수테스트
인수테스트는 고객 또는 최종 사용자가 주도한다
1. 요구한 기능을 시스템이 제대로 제공하는가
2. 실제 사용자가 업무를 수행하기에 편리한가

로그인

문제가 발생했을 때 업무나 사용자에게 미치는 영향이 크기 때문이다.

로그인 기능에서 이미 많은 결함이 발견되었으므로 아직 발견되지 않은 결함도 더 존재할 가능성이 있다 따라서 추가 테스트를 집중해야 한다

100개의 테스트가 모두 성공했다고 하더라도 시스템에 결함이 없다고 단정할 수 없다. 테스트는 결함이 존재함을 보여줄 수는 있지만, 결함이 전혀 없음을 증명할 수는 없다.

모든 결함을 반드시 수정하지 않는 이유
- 프로젝트 일정 부족
- 수정 비용이 지나치게 큼
- 발생 가능성이 매우 낮음
- 수정으로 다른 기능에 문제가 생길 위험
- 업무 영향도가 매우 낮음

어플리케이션 결함 조치 우선순위 결정하기
1. 결함에 대한 개선 방안 확인하기
1-1. 결함 목록과 개선방안을 확인한다
- 테스트 결함 목록을 확인한다
- 결함 목록의 세부사항과 개선 방안 확인
1-2. 테스트별로 결함에 대한 원인 분류
- 결함에 대한 내용을 파악하고 결함 유형을 정의
- 결함 관리 대장을 확인하고 결함 유형을 분류한다
1-3. 결함의 개선 방안 범위를 지정
- 개선할 테스트 케이스 ID를 선정한다
ㄴ 결함관리 대장에서 발견된 결함에 대해 개선 대상을 선정하고 결함 검증 방법을 제시한다.
ㄴ 가장 접근 빈도가 높은 업무, 중요 업무 또는 비기능적으로 반드시 점검해야 할 부분을 선정하여 진행한다
- 개선 조건과 범위를 설정한다
1-4. 결함 유형별로 개선 효과를 정의한다
- 프로젝트 성격에 따라 결함 유형별로 개선 효과는 다르게 작성되며, 개발자, 시스템, 서비스 사용자, 서비스, 아키텍트 관점 등 테스트의 목표에 따라 개선 효과는 다르게 정의된다.

2. 개선 방안에 대한 우선순위를 결정한다
2-1. 업무별 기준에 가중치 부여하기
- 업무/서비스 중요도를 파악하기 위해 이전 시스템의 접속 로그와 업무 일일 데이터 처리량을 통해 작성
- 시스템 의존도는 시스템 없이 수작업이 가능한 업무와 불가능한 업무로 나누어 작성
- 사용자 범위는 현재 사용 대상의 범위와 향후 변경되는 시스템의 확대 가능성을 판단하여 작성한다
- 월 이용자 수는 현재 전담 인력과 공통 성분을 포함하여 월 이용자 수를 산정하고 전체적인 평균치를 고려해서 작성한다
2-2. 단위 업무와 연결하여 심각도를 계산한다.
- 단위 업무별 평가등급을 부여한다
- 단위 업무별 심각도를 계산한다
ㄴ 단위 업무별 가중치 (업무/서비스 등급 * 0.3) + (시스템 의존도 * 0.2) + (사용자 범위 등듭 * 0.3) + (월 이용자 수 등급 * 0.2)로 계산
ㄴ 가중치의 심각도를 측정하기 위해 표시 단위와 측정 구간을 정의한다
HIGH : 단위 업무 프로세스가 비정상적으로 수행되고, 해당 프로세스로 인하여 다른 단위 기능 또는 시스템의 전반적인 기능에 장애가 발생하는 경우의 결함 측정 구간은 가중치 4.0 이상
MEDIUM : 단위 업무 프로세스가 일반 사용자 환경에서는 정상적으로 완료될 수 없는 경우의 결함 가중치 3.0 이상 4.0 이하
Low : 단위 업무 프로세스가 일반 사용자 환경에서는 정상적으로 완료될 수 있으나, 특정 사용자는 정상적으로 완료될 수 없는 경우의 결함

ㄴ 단위 업무별 심각도를 계산한다

2-3. 부여된 가중치와 심각도를 고려하여 우선순위를 결정한다
- 정량적으로 나타난 결함 심각도를 바탕으로 결함 조치의 우선 순위를 나열하며, 업무별 담당자와 팀별 회의를 통해 정성적으로 평가하고 구분한다. 이때 업무별로 결함 심각도가 가장 높다고 해서 그 결함을 무조건 수행해야 하는 것은 아니다.
- 긴급, 높음, 보통, 낮음으로 표현 순위를 나타내며, 각 우선순위에 따라 인력 배치와 결함 조치 일정을 결정한다
