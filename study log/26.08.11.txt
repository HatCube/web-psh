소프트웨어 개발 생명주기와 V 모델
소프트웨어 아키텍스 : 요구사항 분석 및 설계 담당
테스트 매니저 : 검증 및 테스트 담당
둘이 서로 보완관계를 형성한다.

V모델 : 소프트웨어 개발 과정과 테스트 과정을 서로 대응시켜 표현한 개발 테스트 모델

요구 분석 <-> 인수 시스템 
- 사용자 요구사항이 실제 시스템에 제대로 반영되었는지 검증
아키텍처 설계 <-> 시스템 테스트
- 전체 시스템의 기능 / 비기능 요구사항 및 인터페이스 작동 여부 검증
모듈 설계 <-> 통합 테스트
- 모듈 간 인터페이스 및 데이터 연동 검증 
구현 <-> 단위 테스트
- 개별 단위 컴포넌트 또는 모듈의 로직 검증

프로젝트 단계별 테스트 분류
단위테스트
- 최소 단위(모듈,클래스,함수 등)의 소스코드가 설계대로 동작하는지 검증
- 주로 개발자가 구현 직후 작성하여 수행한다
- 구조 기반 테스트(화이트 박스)
- 명세 기반 테스트(블랙 박스)
통합 테스트
- 단위 테스트를 통과한 모듈들을 결합하여 모듈 간의 인터페이스 및 데이터 흐름의 오류를 검증한다
- 빅뱅, 상향식(Driver),하향식(Stub),샌드위치,중앙식,협업식,레이어 통합등의 테스트 방식이 있다.
시스템 테스트
- 단위 및 통합을 거친 완제품 형태의 전체 시스템이 기능적,비기능적 요구사항을 충족하는지 환경 전반에서 검증 
- 명세서 기반의 블랙박스 테스트
- 성능,회복,보안,부하 테스트
인수 테스트
- 실제 사용자 / 고객이 운영 환경과 유사한 조건에서 요구사항 충족 여부를 최종 검증한다.
- 사용자 인수 테스트
- 운영상의 인수 테스트
- 계약 인수 테스트
- 알파 테스트
- 베타 테스트

테스트 기반에 따른 테스트 종류
구조 기반
- 소프트웨어 내부의 논리 흐름에 따른 테스트 케이스 작성 및 결함 발견 활동
- 구문 기반,결정 기반,조건 기반,조건 결정 기반,변경 조건 기반, 멀티 조건 기반 커버리지
명세 기반
- 사용자의 요구사항 분석서에 주어진 명세를 빠뜨리지 않고 테스트 케이스화
- 동등 분할, 경곗값 분석, 결정 테이블 테스팅, 상태 전이 테스팅, 유스케이스 테스팅
경험 기반
- 유사 소프트웨어나 기술에서의 테스터의 경험,직관,기술 능력을 바탕으로 하는 테스트 기법
- 탐색적 테스팅, 리스크 기반 테스팅

테스트 자동화 도구
테스트 자동화
테스트 절차를 자동화 도구를 활용하여 준비,구현,수행,분석 등을 스크립트 형태로 구현함으로써, 시간과 인력 투입의 부담을 최소화 하면서 운영 중인 시스템을 모니터링 하거나 UI사 없는 서비스의 경우에도 정밀한 테스트가 가능하도록 하는것 

장점
- 테스트 데이터의 재입력과 재구성 같은 반복 작업을 자동화 하여 인련과 시간을 최소화 한다
- 향상된 요구사항 정의, 성능 및 스트레스 테스트, 품질 측정을 최적화한다.
- 빌드 확인,회귀,다중 플랫폼 호환성, 소프트웨어 구성, 기본 테스트 등의 향상된 테스트 품질을 보장한다.

단점
- 테스트 도구 전문가 양성 또는 고용이 필요하며, 초기에 프로세스 적용에 대한 시간,비용,노력에 대한 추가 투자가 필요하다.
- 비공개 상용 프로그램의 경우 고가이며, 인력과 교육에 대한 유지관리 비용이 비싸다.

테스트 자동화 수행 시의 고려사항
- 재사용 및 측정이 불가능한 테스트 프로그램은 제오
- 반복적인 빌드에서 스크립트 재사용성이 가능해야 한다.
- 모든 수동 테스트 과정을 자동화할 수는 없다.
- 도구 환경 설정과 도구 습득 기간을 고려하여 프로젝트 지연을 방지해야 한다
- 테스트 엔지니어를 늦게 투입하면 프로젝트에 대한 이해 부족으로 불완전한 테스트를 초래할 수 있으므로, 적절한 투입 시기와 계획을 프로젝트 초기에 수립해야 한다.

테스트 도구 평가 방법 및 요소
평가 방법
- 도구가 지원하는 모든 사항에 대해 종류별로 나열, 기록
- 테스트에 해당하는 요소에 대한 목표 또는 평균값을 설정하고 설정된 기준으로 평가한다
- 비용을 최소화 하기 위해 필수적인 몇가지 요소만을 고려해야할 경우 최소한의 요구사항을 만족하는 도구 선정

평가 요소
- 도구의 사용 편의성
- 다중 사용자 접속
- 결함추척
- 도구 기능성
- 보고 능력
- 성능 및 스트레스 테스트
- 버전 제어
- 테스트 계획과 관리
- 가격
등의 객관적이고 수치화되는 항목을 이용하여 평가

어플리케이션 테스트 수행하기
1.테스트 계획서 확인하기
- 테스트의 목적과 범위를 확인
ㄴ목적 : 업무 흐름별 경로의 적절성, 각 어픞리케이션 간 연계 및 연동확니, 기능과 비기능의 적합성 및 사용 편의성 확인
ㄴ범위 기간과 자원에 따라 범위가 달라진다 5일간의 일정으로 진행할 때, 적게는 5개에서 10개 이내의 기능을 선정하여 테스트한다.

- 테스트 실행 계획을 확인한다
ㄴ시작,종료 기준을 확인한다.
시작 : 개발 진척률이 50%이상일 때 단위 테스트 시작
종료 : 중대한 결함이 조치되거나,결함의 영향이 크지 않으면 종료
ㄴ테스트 수행 절차 확인 : 테스트 관리자, 업무 그룹, 기술 지원 등 역할과 보고 체계를 확인한다.

테스트 케이스르 확인한다
ㄴ테스트 시나리오 확인하기
ㄴ테스트 케이스 확인하기
- 테스트 데이터 확인하기
ㄴ테스트가 진행되는 동안 데이터의 변경(생성,수정,삭제)작업이 밸생ㅅ할 수 있으므로 테스트 상황에 맞는테 스트의 생성 및 유지 방침을 확인해야 한다
ㄴ테스트 수행시 별도의 데트스 데이터가 구성되면 좋으나 만힝 실 운영 데이터를 사용할 경우에는 특히 데이터의 유지 절하를 고려해야 한다.

- 테스트 환경을 확인한다
ㄴ테스트 대상 장비,테스트 도구, 테스트용 데이터,네트워크 환경 등 테스트와 관련된 일반적인 IT자원과 도구를 명시하고 자원별 담당 부서는 사전 점검 항목을 참고하여 테스트 수행을 위한 최소 수준 이상의 환경 구성 여부를 확인한다.
ㄴ테스트에 사용할 도구를 확인한다
도구들을 테스트 단계에 따라 분류하면 테스트 생성, 수행,관리 도구로 나뉜다.
테스트 수행 도구 : 실제 프로그램을 실행하면서 테스트하는 도구

테스트 관리 도구 : 테스트 케이스를 관리, 테스트 결과 기록, 결함 등록 결함 담당자 지정,결함 상태 관리, 수정 유부 추적을 해주는 도구

결함 관리 프로세스
1.결함 관리 계획
- 전체 프로세스에서 결함 관리에 대한 일정,인력,업무 프로세스를 확보하여 계획을 수립하는 것
문서결함 
- 기획자,사용자,개발자 간의 의사소통과 가록이 원할하지 않은 경우에 발생하는 결함
- 사용자의 온러안,오프라인 메뉴얼 불일치
- 요구사아 분석서와 기능 요구사항의 불완전한 상태의 문서

결함 심각도
- 여러개의 결함 중 전체 시스템에 결함이 미치는 영향을 레벨별로 나타내는 것

High
- 시스템이 중단되어 더이상 프로세스를 진행할 수 없게 만드는 결함
- 핵심 요구사항 미구현, 시스템 다운, 장시간 시스템 응답 지연, 시스템 복구 후 데이터 왜곡등
Medium
- 시스템의 흐름에 영향을 미치는 결함
- 부정확한 기능,부정확한 업무 프로세스, 데이터 필드 형식의 오류, 데이터베이스 에러, 보안 관련 오류
Low
- 시스템의 흐름에는 영향을 미치지 않는 결함이나 상황에 맞지 않는 용도와 화면 구성의 결함
- 부정확한 GUI 및 메시지,에러시 메시지 미출력, 화면상의 문법 / 절차 오류

결함 관리하기
1.어플리케이션 테스트 수행으로 발견된 결함을 기록하고 분류

분류
- 발견된 결함을 관리할 테스트 관리 양식을 작성
관리할 항목 정의
테스트 ID 항목 생성 
테스트 시나리오명 항목 생성
테스트 케이스명 
테스트 수행 결과
테스트 담당자,계획일,수행일 항목을 생성
결함 내용 항목
추가하고 싶은 내용이 있다면 추가

- 기록된 테스트 관리 양식의 결함을 유형별로 분류하고 결함 상태를 확인한다
분석 : 요구사항의 표준 미준수, 테스트 불가능, 불명확
설계 : 설계 표준 미준수, 테스트 불가능, 불명확,불일치
개발 : 개발 표준 미준수, 불완전, 불일치, 인터페이스 결함
테스트 : 업무 이해 부족, 팀 간 의사소통 부족, 개발자 실수

발생한 결함에 대한 결함 상태를 정의
Open : 결함이 보고되었지만 아직 분석되지 않은 상태
Assigned : 결함을 개발자에게 할당한 상태
Fixed : 개발자가 결함을 수정한 상태
Closed : 결함이 수정되었는지 확인하고 회귀 테스트 시 결함이 발견되지 않은 상태(수정된 결과가 만족스럽지 않을 경우, 결함의 상태를'Open'으로 변경한다)
Deferred : 결함 우선 순위가 낮게 분류되었기 때문에 결함 수정을 연기한 상태
Clarified : 보고된 결함이 프로젝트 팀에 의해 결함이 아니라고 판단된 상태

정의한 결함 유형을 이용하여 결함 관리 현황을 결함관리표에 결함 상태를 같이 작성한다

ㄴ시스템 장애와 어플리케이션 장애로 나눌 때 시스템 장애는 인프라 아키텍처 팀 등에서 별도로 담당하여 진행하도록 하고, 소프트웨어 아키텍트는 어플리케이션 장애 관점에서 복구 테스트를 수행하도록 한다

2.결함 관리의 이해
2-1.결함 관련 용어
- 에러(Error)
ㄴ소프트웨어 개발 또는 유지 보수 수행 중에 발생한 부정확한 결과로, 개발자의 실수로 발생한 오타,개발 명세서의 잘못된 이해, 서브루틴의 기능 오해등이 있다.
- 오류(Fault)
ㄴ프로그램 코드상에 존재하는 것으로 비정상적인 프로그램과 정상적인 프로그램 버전 간의 차이로 인하여 발생되며,잘못된 연산자가 사용된 경우에 프로그램이 서브루틴으로부터의 에러 리턴을 점검하는 코드가 누락된것
- 실패(Failure)
ㄴ정상적인 프로그램과 비정상적인 프로그램의 실행 결과의 차이를 의미하며, 프로그램 실행 중에 프로그램의 실제 실행 결과를 개발 명세서에 정의된 예상 결과와 비교함으로서 발견한다.
- 결함(Defect)
ㄴ버그, 에러, 오류, 실패, 프로그램 실행에 대한 문제점, 프로그램 개선사항등의 전체를 포괄하는 용어

2-2.결함 판단의 기준
- 기능 명세서에 가능하다고 명시된 동작을 수행하지 않는 경우
- 기능 명세서에 불가능하다고 명시된 동작을 수행하는 경우
- 기능 명세서에 명시되어 있지 않지만 수행해야할 동작을 수행하지 않는 경우
- 테스터의 시각에서 볼때 문제가 있다고 판단되는 경우

테스터의 시각에서 결함으로 판단되는 경우
이해하기 어려운 기능,사용이 까다로운 기능,비정상적으로 느린 기능 등

3.테스트 격언
3-1.소프트웨어를 완벽하게 테스트 하는 것은 불가능하다.
- 가능한 입력의 수가 너무 많다
- 가능한 출력의 수가 너무 많다
- 소프트웨어 명세서가 주관적이다
- 소프트웨어 결함도 주관적이다.
3-2.소프트웨어 테스트는 위험을 수반하는 훈련이다
- 가능한 모든 테스트 시나리오와 테스트 케이스를 테스트 하지 않을 경우 위험을 감수하기로 했다는 뜻과 같다
- 테스터는 무엇이 중요하고, 중요하지 않은지 현명한 판단을 하여야한다.
3-3.테스트 작업으로 결함이 존재하지 않는다는 사실을 입증할 수 없다
- 테스트를 통해 소프트웨어 결함이 없다는 것을 보장할 수는 없으며,단지 테스트 결과로 결함이 있다는 사실만을 보여줄 수 없다.
- 테스트 결과 결함이 발견되지 않았다 하더라고 이는 결함이 없음을 의미하는 것은 아니다.
3-4.아래와 같은 사유로 인하여 발견한 모든 결함을 수정할 수는 없다 .
- 쫓기는 작업 일정
- 외부적 요인으로 결함이 아님에도 결함으로 판단되는 경우
- 각각의 프로그램 간에 서로 결합도가 높은 경우의 고치기 위험한 결함
- 현실에서 거의 발생할 가능성이 없는 경우의 고칠 가치가 없는 결함
3-5.발견한 결함이 많을수록 남아있는 결함의 수도 많다.

4.소프트웨어 테스터의 역할과 능력
4-1.소프트웨어 테스터의 역할
- 가능한 결함을 빨리 발견하여 결함이 수정,보완되었는지 확인하는것이다
4-2.소프트웨어 테스터의 능력
- 탐구심과 문제 해결혁을 갖춰야 한다.
- 때로는 창의력을 발휘하여 결함을 찾기 위해 새로운 접근법도 사용해야 한다.
- 완벽함을 추구하지만, 가능한 한도 내에서 적당한 수준의 완벽성을 추구한다.
- 테스터는 항상 나쁜소식을 전하는 사람이다.개발자에게 결함이 있다고 말을 해야한다.

    ↓

→ 주문 완료 처리

문제 9. 장애 복구 테스트

다음과 같이 웹 서비스를 운영하고 있다.

사용자
   ↓
Load Balancer
 ↙       ↘
WAS1    WAS2

현재 WAS1과 WAS2가 동시에 서비스를 제공한다.

장애 복구 테스트를 위해 사용자가 서비스를 이용하고 있는 상태에서 WAS1 프로세스를 강제로 종료하였다.

문제

이 테스트의 목적과 정상적인 예상 결과를 서술하시오.

장애 복구 테스트
테스트 목적 > 하나의 서버에 장애가 발생하더라도 전체 서비스가 중단되지 않고 정상적으로 지속되는지를 확인하는것
예상 결과 > WAS1을 강제로 종료했을때 로드 밸런서가 사용자 요청을 정상 상태의 WAS2로 전달해야 한다
따라서 사용자는 서버 장애를 인식하지 못하거나 최소한의 영향만 받은 상태에서 서비스를 계속 이용할 수 있어야 한다.

문제 10. Error, Fault, Failure, Defect 판단

회원가입 요구사항은 다음과 같다.

만 20세 이상인 사용자만 가입할 수 있다.

개발자가 요구사항을 구현하면서 실수로 다음 코드를 작성하였다.

if (age > 20) {
    register();
}

그 결과 20세 사용자가 회원가입을 시도했지만 가입이 거부되었다.

문제

위 상황을 다음 네 가지 개념과 연결하여 각각 설명하시오.

Error : 개발자가 >=로 작성해야 하나 >로 작성한 사람실수
Fault : 잘못 작성된 조건 age > 20자체를 의미
Failure : 프로그램을 실행했을때 사용자가 실제로 회원 가입에 실패한 현상
Defect : 위의 Error,Fault,Failure를 포함한 관리되는 문제 전체를 의미
